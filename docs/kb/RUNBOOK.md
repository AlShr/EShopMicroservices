# Project knowledge runbook (gstack + gbrain)

A step-by-step guide to index this project, keep a small knowledge base in
gbrain, use gbrain as memory for Claude Code, and adopt gstack skills.
Phases 1-5. Reusable on other projects (see the last section).

What we learned from evaluating gbrain on this repo is in
`docs/kb/_verification/phase2-gbrain-native.md`. The short version:

- **gbrain is worth it as memory**, for knowledge that isn't in the code:
  decisions, team rules, pitfalls found the hard way. In the A/B test, a saved
  fact let Claude answer in 1 call, 65% cheaper than searching the repo.
- **gbrain isn't worth it for code lookup on a repo this size.** Claude reads
  the code anyway; with gbrain connected, code questions cost 25-46% more for
  the same answer.
- So: **don't write a big knowledge base up front.** Save short, checked facts
  and a few pages about what the code doesn't say, as you learn them.

## How it fits together

| Layer | What's in it | Where it lives | How it gets into gbrain | How you read it |
|---|---|---|---|---|
| **Code index** (source `gstack-code-6651f992-3f84fc`) | Every code file, symbol and call | The repo | `gbrain sync` (strategy `code` is saved for this source) | `gbrain code-def`, `code-callers`, `query` |
| **Facts** (same code source) | Short statements: "we chose X because Y", "never do Z" | gbrain only | `gbrain remember … --source-id gstack-code-6651f992-3f84fc`, or ask Claude to remember it | `gbrain recall`, or Claude over MCP |
| **Knowledge base pages** (source `default`, slugs `eshop/…`) | Reviewed pages about decisions, flows, pitfalls | `docs/kb/pages/eshop/*.md` in git | `gbrain put eshop/<name> --source-id default < file` | `gbrain query … --source-ids gstack-code-6651f992-3f84fc,default`, `gbrain get --source default -- eshop/<name>` |

**Run terminal commands from the repo root.** In Claude Code, put `!` in front
of a command (`! gbrain query "..."`) so Claude sees its output too.

**Before you start:** Docker Desktop must be running (gbrain's Postgres
`gbrain-postgres` runs there). Quick check: `docker ps` and `gbrain doctor`.

### Folder layout

```

  pages/

      <page>.md

    think/                  <- answers generated by `gbrain think`
    ab/
      summary.sh            <- summarise A/B runs
      set-surface.sh        <- switch the gbrain MCP surface
```

### Rules that keep gbrain useful (learned the hard way)

1. **Keep documentation out of the code source.** When Markdown about the code
   (KB pages, notes, generated answers) was indexed next to the code, search
   ranked it above the code, and a pinned question "refreshed" itself from an
   old answer instead of the config file. The code source now syncs with
   strategy `code`, which skips Markdown.
2. **Everything is scoped by source.** This repo is pinned to the code source
   (`.gbrain-source`), so a plain `search`, `query`, `recall` or `forget` here
   only sees the code source. Pass `--source-id default` (`--source default`
   for `forget`) to reach KB pages, or `--source-ids <code>,default` for both.
   **Facts for EShop sessions must be saved in the code source**, or Claude
   won't find them.
3. **KB pages can't be a separate synced source inside this repo.** gbrain
   refuses (`overlapping_path`) because the code source covers the repo root,
   and `gbrain import` refuses files inside another source's folder. Load each
   page with `gbrain put` instead.
4. **`gbrain delete` also deletes the file** from the source's folder, which
   for the code source is this repo. Restore it with `git restore <file>`.
5. **The MCP server runs on the `starter` surface** (memory verbs and about 20
   operations instead of 189). Switch with
   `bash docs/kb/_verification/ab/set-surface.sh starter|full`.

## Phase 1: Index and check retrieval (~30 min)

**1.1 Sync.** In Claude Code:

```
/sync-gbrain --full
/sync-gbrain --dream
```

Pass when both end with `OK code` and `OK dream`. If the memory row shows
`ERR`, run `/sync-gbrain` once more. That error is transient.

After code changes, a plain `gbrain sync` is enough: the saved `code`
strategy picks up code files. (Before the strategy was saved, a plain sync
only read Markdown and silently skipped code changes.)

**1.2 Find definitions.** Pick about 15 class names from different services
and look each one up:

```
! gbrain code-def CachedBasketRepository
! gbrain code-def DiscountService
! gbrain code-def ApplicationDbContext
```

Pass when `count` ≥ 1 and the file path is correct.
Known limitation: `record` types (commands, queries, events) always return 0.
Use `gbrain query` or Grep for them.

**1.3 Call graph.** Always query a **method** name, never a class name:

```
! gbrain code-callees DeductDiscount        # expect GetDiscountAsync (Basket→Discount gRPC)
! gbrain code-callers Publish               # expect 3 callers (2 MassTransit, 1 MediatR)
! gbrain code-callers CreateNewOrder        # expect CreateOrderHandler.Handle
! gbrain code-callers GetBasket             # who reads baskets
```

Read the `from_symbol_qualified` field to see who the caller is. Edges are
never linked to the method they call (`resolved: false`), so methods with the
same name (`Handle`, `Publish`, `GetBasket`) get merged. Calls between services
(gRPC, RabbitMQ) don't appear in the graph at all.

**1.4 Plain-English questions.** Ask about 10 questions where you already know
the answer:

```
! gbrain query "where is the discount applied to the basket price"
! gbrain query "how does checkout create an order"
```

Pass when the correct file is in the top 5. Known weak spots: top-level
`Program.cs` code (all DI wiring) is never retrieved, and comments (including
stale TODOs) rank like code.

**1.5 Save the results** in `docs/kb/_verification/phase1-scorecard.md`: each
check with hit/miss and a score.

Baseline (2026-11-11, gbrain 0.60.645.0, commit 9b924da):

| Check | Score |
|---|---|
| Finding definitions of classes and interfaces | 17/17 |
| Finding definitions of C# records | 0 (not indexed; 87 records in repo) |
| Who-calls-what between methods | 8/8 |
| Each call linked to the method it calls | none are linked |
| Plain-English questions, top 5 | 11/12 |

## Phase 2: Build the knowledge base (as you learn, not up front)

The evaluation showed that pages restating what the code already shows don't
pay off: they go stale, crowd the code out of search results, and repeat
mistakes. Write down only what the code doesn't tell you.

**What to save, and where:**

| Kind of knowledge | Example | Save as |
|---|---|---|
| A one-line rule, decision or pitfall | "Ordering ignores basket items and creates orders with 2 hardcoded items (`BasketCheckoutEventHandler.cs:34-38`)" | **Fact** in the code source |
| A flow or decision that needs a few paragraphs | Why Discount uses gRPC; the checkout sequence and its failure modes | **KB page** in `docs/kb/pages/eshop/` |
| A fact that may change when the code changes | "Which feature flags exist and what do they control?" | **Pinned question** (Phase 2c) |

### 2a. Save a fact

```
! gbrain remember "<one claim, with path:line if it's about code>" --entity "<topic, e.g. EShop Ordering service>" --source-id gstack-code-6651f992-3f84fc --content-origin user_said --provenance "<where it came from>"
! gbrain recall <entity-slug>
```

Or, in a Claude Code session: "Remember in gbrain: …". Claude saves it with
the `remember` tool.

Good first facts from the evaluation: the hardcoded order items, the
`OrderFullfilment` flag being `false` in appsettings but `true` in
docker-compose, Basket's validators never being registered, and the stale
TODO in `DeleteBasketHandler` (the cache *is* cleared).

### 2b. Write a KB page

**Step A. Draft.** Write it yourself, or ask Claude with a prompt like:

> Write `docs/kb/pages/eshop/<name>.md`. Topic: <topic>. Read the code to
> confirm every claim and back it with a `path:line` reference. Mark anything
> you could not verify as **UNVERIFIED**. Start the file with frontmatter:
> `title`, `tags: [eshop, kb]`, `updated: <date>`.

**Step B. Review it yourself.** Spot-check 2-3 `path:line` references. This is
the quality gate; gbrain has no review step of its own.

**Step C. Commit it, then load it into gbrain:**

```
! git add docs/kb/pages/eshop/<name>.md && git commit -m "docs(kb): add <name> page"
! gbrain put eshop/<name> --source-id default < docs/kb/pages/eshop/<name>.md | grep -E '^  "(slug|state|embedding_state)"'
```

**Step D. Check that it can be found**, also with wording that doesn't match
the title:

```
! gbrain query "<a question the page answers>" --source-ids gstack-code-6651f992-3f84fc,default
! gbrain get --source default -- eshop/<name>
```

Pass when your page is in the top 5.

**When the code changes later:** edit the `.md` file, commit, and run the same
`gbrain put` again. It replaces the whole page. There is no automatic sync for
these pages.

Don't bother with `gbrain link` or `gbrain extract`: gbrain's automatic linking
is built for people and companies and produced no links for code pages.

### 2c. Pin questions you want to watch

```
! gbrain questions pin "<question>" --source gstack-code-6651f992-3f84fc
! gbrain questions list
```

After a code change and sync, `questions list` marks exactly the sentences
that went stale. Refreshing is manual (`gbrain questions refresh <id>`), and
check the refreshed answer yourself: it can bring an old fact back if any
document in the source still states it.

## Phase 3: Memory test across sessions (~20 min)

This tests gbrain's main promise: Claude remembering something in a new
session that it couldn't find in the code.

**1. Pick a fact that isn't in the code and can't be guessed.** Prove it:

```
! grep -r -i "<a distinctive word from the fact>" src docs
```

**2. Save it with the CLI** (not through Claude, so Claude Code's own memory
files can't hold a copy), in the code source:

```
! gbrain remember "<fact>" --entity "<topic>" --source-id gstack-code-6651f992-3f84fc --content-origin user_said --provenance "memory test <date>" --ttl 7d
! gbrain recall <entity-slug>
```

The plain `recall` (no `--source-id`) must find it. That's the scope Claude's
gbrain server uses in this repo.

**3. Ask in fresh sessions, with and without gbrain:**

```
! echo '{"mcpServers":{}}' > /tmp/no-mcp.json
! claude -p "<question only the fact answers>" --strict-mcp-config --mcp-config /tmp/no-mcp.json --allowedTools "Read,Grep,Glob" --output-format stream-json --verbose > docs/kb/_verification/ab/mem-without-1.jsonl
! claude -p "<question only the fact answers>" --allowedTools "Read,Grep,Glob,mcp__gbrain" --output-format stream-json --verbose > docs/kb/_verification/ab/mem-with-1.jsonl
! bash docs/kb/_verification/ab/summary.sh mem -a
```

Both sides get the same pre-approved read-only tools; only gbrain differs.
Without `--allowedTools "…mcp__gbrain"`, `claude -p` silently refuses gbrain's
tools and the test is invalid. Paste each command on one line.

**Score it:**

- ✅ **Pass:** the "with" answer contains the fact and `summary.sh` shows a
  gbrain call that ran; the "without" answer says it can't tell.
- ❌ **Fail:** no gbrain call (Claude didn't think to check), or a gbrain call
  that found nothing (check the source scope: rule 2 above).

**4. Clean up:** `! gbrain forget <fact-id>` (add `--source default` for a fact
saved in `default`).

Result on 2026-11-12: pass once the fact was in the code source (1 call,
quoted exactly, $0.09 vs. $0.26 without). Details in
`docs/kb/_verification/phase2-gbrain-native.md`.

## Phase 4: gstack skills (one at a time)

| Order | What you do | Pass |
|---|---|---|
| 1 | Ask Claude: "Add an xUnit test project `Basket.API.Tests` with tests for `StoreBasketCommandHandler.DeductDiscount`, with the gRPC client mocked." The repo has no tests, so `/verify` has nothing to run | `dotnet test` is green |
| 2 | `/verify` | Build and tests are green. Then break a test on purpose and run it again: it must go red |
| 3 | `git checkout -b test/review-check`. Plant a bug yourself, e.g. apply the discount twice. Commit, then run `/review` | `/review` finds the bug |
| 4 | Start Docker Desktop, then `docker compose -f src/docker-compose.yml -f src/docker-compose.override.yml up -d`, then `/qa` | It completes the catalog → basket → checkout → order flow. Check that any bug it reports is real |
| 5 | Later, adding each one only after the previous one has run cleanly twice: `/ship`, `/health`, `/cso`, `/retro` | — |

**Save results:** gstack keeps its own reports under `~/.gstack/`. Write a
one-line verdict for each skill in `docs/kb/_verification/phase4-skills.md`.

## Phase 5: Full loop on one real feature

Run these in order and keep the knowledge up to date as you go:

```
/spec "minimum order amount at checkout"
→ ask Claude to implement it ("check gbrain for facts about checkout first")
→ /verify → /review → /qa → /ship
→ save new decisions and pitfalls as facts (code source)
→ update docs/kb/pages/eshop/<page>.md if a page covers checkout → gbrain put eshop/<page> …
→ gbrain sync
```

Track two things: whether Claude recalls saved facts instead of rediscovering
them, and bugs caught before the PR.

## Reusing this on another project

1. `/setup-gbrain`, then `/sync-gbrain --full`
2. `gbrain sources set-strategy <code-source-id> code`, so Markdown stays out
   of the code index
3. Register the MCP server with a smaller surface (`serve --surface starter`)
4. Create `docs/kb/pages/<name>/` for reviewed pages and load them with
   `gbrain put <name>/<page> --source-id default`
5. Save facts in the project's code source, not `default`
6. Rerun the Phase 1 checks and the Phase 3 memory test
